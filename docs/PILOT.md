# Первый рабочий цикл

Это инструкция начального импорта и персонального входа. Для нового запуска с примерами, редактором задач, обсуждениями и документами смотри **[полный прототип](PROTOTYPE.md)**.

Рабочее пространство использует те же данные, правила и память SQLite, что и агент. Отдельный процесс пилота не запускает модель и сообщения Telegram; включаемый автоопрос внутри приложения проверяется раз в минуту. Он позволяет пройти цикл сотрудника и руководителя до подключения внешних сервисов.

Опубликованный сайт Sites остаётся демонстрацией. Рабочий интерфейс открывается на адресе запущенного сервера: `/assistant/workspace`.

## Быстрый запуск на своём компьютере

Нужен Node.js 24. Команды выполняются из корня репозитория.

```sh
npm ci
npm run pilot:import -- config/pilot.example.json
npm run pilot:serve
```

Импорт предназначен для пустой базы и не перезаписывает имеющиеся задачи. В примере используются вымышленные участники. Перед рабочим пилотом подготовьте свой JSON по его структуре и проверьте даты.

Откройте `http://127.0.0.1:8787/assistant/workspace`.

Во втором терминале из того же каталога выпустите персональный код для сотрудника:

```sh
npm run pilot:invite -- employee-1
```

Скопируйте полученный код в форму входа. Он действует 30 минут и принимается один раз. Новое приглашение тому же участнику отменяет его предыдущий неиспользованный код. Вход создаёт сеанс на 8 часов; выход отзывает текущий сеанс. В базе сохраняются хеши кодов и сеансов. Коды нельзя включать в URL, Git, скриншоты или общие журналы.

Для руководителя откройте отдельный профиль браузера или приватное окно и используйте другой код:

```sh
npm run pilot:invite -- manager
```

Два профиля нужны, чтобы браузер не подменял персональную cookie одним и тем же сеансом.

## Отключение доступа сотрудника

Руководитель открывает «Участники» → «Отключить доступ» у нужного сотрудника и подтверждает действие. Сервер одной транзакцией отключает вход, отзывает все его веб-сеансы и неиспользованные коды приглашения. Уже открытая вкладка больше не сможет читать или сохранять данные при следующем запросе; ранее загруженное содержимое браузера удалённо не стирается. Новые коды входа, в том числе через CLI, для отключённого сотрудника запрещены.

Сотрудник остаётся в списке со статусом «Доступ отключён». Его поручения, авторство сообщений и история сохраняются; переназначение поручений выполняется отдельно. Повтор подтверждённого запроса безопасен. Отключение руководителей и восстановление доступа этим действием не предусмотрены. Связанный вход через Telegram и инструменты агента также отклоняются. Отключённому сотруднику нельзя назначить новое поручение или переназначить чужое. У существующего поручения можно менять описание и срок, сохраняя прежнего исполнителя. Это управление доступом одной команды, не изоляция нескольких организаций и не удаление сторонних учётных записей.

## Что проверить руками

1. Сотрудник видит только свои поручения. Откройте П-001 и отправьте: «Прошу перенести срок на 2026-10-20: данные ещё не получены». При необходимости замените дату на актуальную.
2. Руководитель нажимает «Обновить данные» и открывает то же поручение. Видны исходное сообщение, предложенная дата и прежний утверждённый срок.
3. Нажмите «Согласовать срок». Изменение появляется в истории с автором; сотрудник после обновления видит тот же срок.
4. Отправьте «Работа не выполнена». Такое сообщение не должно стать готовностью к приёмке.
5. Откройте карточку руководителя, затем отправьте ещё одно обновление сотрудника. Попытка решения по старой карточке должна попросить проверить новые данные.
6. Перезапустите сервер. Задачи, сообщения, решения и ещё действующие персональные сеансы должны сохраниться.

Подготовленные черновики видит руководитель. В полном прототипе доступны создание и редактирование задач, этапы, обсуждения, подготовка и правка документов. Согласованный текст можно скачать; внешняя отправка — отдельное действие, которое этот процесс не выполняет.

## Конфигурация

| Параметр | Назначение |
| --- | --- |
| `ASSISTANT_DATA_DIR` | Один и тот же постоянный каталог для пилота, приглашений, резервных копий и eve. По умолчанию `.data` |
| `ASSISTANT_SERVER_ORIGIN` | Точный адрес без пути: например `https://assistant.example.org`. Для локального запуска автоматически используется `http://127.0.0.1:8787` |
| `ASSISTANT_HOST` | Интерфейс прослушивания; по умолчанию только `127.0.0.1` |
| `ASSISTANT_PORT` | Порт процесса пилота; по умолчанию 8787 |

Переменные задаются окружением процесса. Скрипты npm автоматически `.env` не читают. При использовании локального `.env` передавайте его явно **во все** команды, которые обращаются к данным:

```sh
node --env-file=.env scripts/import-pilot.mjs /path/to/private-pilot.json
node --env-file=.env scripts/pilot-server.mjs
node --env-file=.env scripts/pilot-invite.mjs employee-1
node --env-file=.env scripts/backup-state.mjs
```

Не включайте рабочую конфигурацию участников, Telegram ID и содержимое базы в Git.

## Развёртывание вместе с агентом

Канал `agent/channels/dashboard.ts` экспортирует те же HTTP-обработчики. После проверенной сборки eve он обслуживает `/assistant/workspace` и `/assistant/api/*`. Каталог `dist/` должен оставаться рядом с исходниками, а рабочий каталог процесса — корнем проекта.

Для рабочего окружения требуются HTTPS, постоянный диск и точный `ASSISTANT_SERVER_ORIGIN`. Основной путь — Node-сервер из [LLM_PROVIDERS.md](LLM_PROVIDERS.md); сборка eve ему не нужна. HTTP разрешён только для loopback-адресов. Обратный прокси должен сохранять публичный Host и маршрутизировать запросы; код не доверяет произвольным `X-Forwarded-*` для выбора адреса.

Установка интерфейса на статический Sites не подключает его к SQLite. Не переносите туда административный токен и не открывайте базу анонимно. Прежде чем назначать сервер, нужно проверить его постоянное хранилище и постоянный запуск Node-процесса.

## Поведение при ошибках

- Статусы не сохраняются в localStorage. После сетевой ошибки интерфейс показывает отсутствие подтверждения; повтор неизменённого действия использует тот же ID.
- Решение содержит версию задачи. Новые сообщения или другие изменения делают старую версию непригодной для записи; пользователь должен просмотреть актуальную карточку.
- После истечения сеанса интерфейс возвращается ко входу. Сервер проверяет участника и его текущую роль, а не параметры из браузера.
- Произвольные внешние сайты не могут выполнять изменения: проверяются Origin и CSRF; cookie — HttpOnly и SameSite=Strict, для HTTPS также Secure.
- Черновик, согласование срока и реальная отправка сообщения — отдельные действия. Процесс пилота не вызывает внешние транспорты.

Перед рабочим запуском нужны процедура отзыва всех сеансов участника, ограничения частоты запросов на входном прокси, внешнее хранение резервных копий и проверка восстановления. Текущие приглашения — механизм закрытого пилота; корпоративный вход рассматривается при масштабировании.

## Проверки

`npm test` и `npm run typecheck`. Новые проверки проходят через настоящие HTTP-обработчики и SQLite: персональный вход, права, сообщения, основания, решения, повтор после потери ответа, устаревшая версия, перезапуск и выдача интерфейса сервером. DOM-проверка не заменяет визуальный просмотр в полноценном браузере.
