# План первого аудита Lazy Work Planer

Подготовлен 16 октября 2026 года по [F27 — Cloudflare security-audit-skill](FINDINGS.md#f27-cloudflare-security-audit-skill). Это план будущей проверки, **не отчёт о найденных уязвимостях и не свидетельство пройденного аудита**.

Цель — до приглашения участников закрытого пилота проверить, может ли внешний текст или пользователь с меньшими правами прочитать чужую задачу, исказить подтверждённую память либо выполнить неодобренное действие.

## Основа и границы

План составлен по `main` на [коммите `e8a67af`](https://github.com/sakrett001-ai/Lazy-work-planer/commit/e8a67afc7f1355d129ab320b953ee38819a8cfe1). Перед запуском фиксируем актуальные commit/tree и чистоту рабочей копии. Уже имеющиеся 91 тест и TypeScript-проверка относятся к предыдущей поставке. Они дают исходные свидетельства, но не заменяют независимый аудит; в рамках подготовки этого плана заново не запускались.

Включаем собственные `agent/`, редактируемый интерфейс `dist/`, серверные скрипты, схемы данных и проверки. `dist/` нельзя исключать как сборочный результат: здесь лежат исходники UI и доменной логики. Не заявляем проверку производственной инфраструктуры, стороннего кода eve, моделей или облачных сервисов только по просмотру нашего репозитория.

Условные участники: руководитель M, сотрудники A/B и неавторизованный посетитель. У каждого синтетические данные. Нынешние роли проверяем как роли одного рабочего пространства; изоляция независимых организаций ещё не реализована и должна получить отдельную модель перед масштабированием.

## Проверяемые границы

Все строки ниже имеют состояние **запланировано**, без назначенной серьёзности.

| Граница | Точки входа и реализации | Минимальная проверка и ожидаемый результат |
| --- | --- | --- |
| Вход и смена прав | `agent/lib/web-auth.ts`, `agent/lib/dashboard-api.ts` | Повтор использованного приглашения, истёкшая сессия, чужой Origin/CSRF и изменение роли. Не возникает нового разрешённого действия; текущая роль читается с сервера. |
| Чужая задача и первоисточник | `agent/lib/assistant-memory.ts`, инструменты чтения, API памяти | Сотрудник A подставляет ID задачи/источника B, меняет offset/версию; доступ меняется между страницами. Ни текст, ни метаданные/сводка чужого объекта не выдаются. Проверяем также старые и альтернативные маршруты чтения. |
| Отравление памяти | `agent/channels/telegram.ts`, `agent/lib/store.ts`, `dist/task-memory.js`, инструменты записи | Сообщение выдаёт себя за инструкцию руководителя, цитата относится к другой задаче, старый источник меняет текст. Авторство и происхождение сохраняются; внешний текст не получает права и не становится утверждённым решением. |
| Намерение и точные параметры | `agent/lib/prototype.ts`, `agent/lib/decisions.ts`, `dist/prototype-ui.js` | Между просмотром и согласованием меняются срок, документ или версия задачи. Старое подтверждение не утверждает новые параметры; согласование документа не означает его отправку. |
| Консультация и поздний результат | `activeWebJob`, `verifyWebEvidence`, `finishAssistantJob`, весь доступный набор инструментов | Чтение/публикация по другой задаче, непрочитанная цитата, отзыв роли, истечение времени и повтор результата. Недопустимый вызов отклоняется, одинаковый результат не дублируется, новая информация видна как устаревание ответа. |
| Доставка и восстановление | `agent/channels/telegram.ts`, `agent/lib/telegram.ts`, расписания и инструменты отправки | Неверный webhook-секрет, неподтверждённый отправитель, повтор, сбой между сохранением и передачей, неизвестный исход отправки. Источник не теряется, не подтверждённая отправка не отмечается успешной и не повторяется вслепую. |
| Вывод и сохранённые данные | `dist/prototype-ui.js`, `agent/lib/dashboard-api.ts`, `scripts/backup-state.mjs` | HTML в сообщении/ответе не исполняется; скачивание документа и чтение копии не обходят права. Секреты, рабочая база и сырые трассы не попадают в публичные артефакты. |

Это начальная карта, а не исчерпывающий список. Проверяющий уточняет реальные маршруты и отмечает найденные пробелы. Наличие инструмента чтения с проверкой доступа не доказывает, что все другие инструменты соблюдают ту же границу.

## Как получать доказательства

1. Выбрать ограниченный профиль/область аудита и зафиксировать изученную ревизию Cloudflare. Рассчитать бюджет по его текущему SKILL с резервом на проверку кандидатов и покрытия. Не выдавать один последовательный просмотр за независимый многоагентный аудит.
2. Подготовить изолированную копию и искусственные записи. Для выполнения проверяемого кода навык требует принудительную изоляцию ОС, отсутствие внешней сети, явный список безопасных переменных, ограниченные права записи и лимиты ресурсов. Обычный worktree сам по себе этих условий не создаёт. Если нужных средств нет, доступный статический разбор продолжается, а решающий непроверенный факт указывается явно.
3. Для кандидата записать атакующего, ресурс, точку входа, трассу до действия, условия, ожидаемый и наблюдаемый исход. Успех промпт-инъекции оценивается нарушением доступа/намерения или сохранённых данных, а не тем, что модель повторила вредную фразу.
4. Отдельный проверяющий пытается опровергнуть кандидата на неизменённом исходном коде. Состояния находок и журнал покрытия проверяются валидаторами. Для `needs_validation` указывается конкретный недостающий факт; отсутствие времени на проверку кандидата отмечается как незавершённая работа, а не как проверенная находка.
5. Исправление идёт отдельным изменением после воспроизведения: проверка выявляет дефект до правки и проходит после неё. Повторно проверяются затронутые границы. Остальные участки не объявляются безопасными по аналогии.

Для первого прохода нужны прежде всего локальные HTTP/SQLite-проверки, управляемые имитации доставки и исходники. Существующие сценарии находятся в `tests/pilot-api.test.mjs`, `tests/assistant-memory.test.mjs`, `tests/prototype.test.mjs`, `tests/prototype-ui.test.mjs`, `tests/server-reliability.test.mjs` и `tests/decisions.test.mjs`. Недостающие проверки добавляем по конкретной гипотезе, без дублирования уже проверяемой реализации.

Проверка поведения живой модели — отдельная часть [E1–E3](AGENT_RESEARCH_2026-10-16.md#очередь-опытов-и-критерии). Имитация ответа модели проверяет серверные ограничения, но не доказывает устойчивость её рассуждений. Доставка настоящим ботом и поведение reverse proxy также получают собственные результаты на выбранном тестовом окружении.

## Результат и следующий шаг

Итогом будущего прохода станут версия исходников, карта фактического покрытия, подтверждённые/опровергнутые кандидаты, отдельные нерешённые вопросы и воспроизводимые проверки. Сырые диагностические материалы с данными доступа в Git не добавляем; для публикации готовим обезличенные результаты.

Перед пилотом разбираем подтверждённые обходы входа, чужое чтение/изменение, незапрошенную отправку и потерю происхождения факта. После исправлений повторяем конкретные проверки. Непроверенные зависимости окружения остаются видимыми условиями запуска.

При готовности HTTPS и Telegram подключаем отдельный мобильный опыт [F28 — ARTEMIS](FINDINGS.md#f28-google-artemis). Он проверяет пользовательский путь на телефоне и дополняет серверные доказательства. Исследование [F29 — карты с глубиной](FINDINGS.md#f29-3d-обозреватель-кода-рика-арендса) идёт после успешного рабочего цикла.
