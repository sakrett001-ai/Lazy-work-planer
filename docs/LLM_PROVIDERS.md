# Подключения ИИ и модели по ролям

Рабочее пространство поддерживает несколько подключений одновременно. У подключения есть провайдер, отдельный ключ и список разрешённых моделей. Для каждой роли руководитель выбирает своё подключение и свою модель в **«Модели и роли»**. Можно завести два подключения VseGPT с разными ключами или использовать один ключ для нескольких ролей.

Этот путь работает через `npm run prototype`, `npm start` или Docker на постоянном Node.js 24 сервере. Учётная запись, хостинг и AI Gateway Vercel не нужны. Исходники старого eve-модуля сохранены отдельно; его модель в `agent/agent.ts` не управляет новой веб-консультацией.

## Что уже работает

| Провайдер в конфигурации | API | Как используется ключ |
| --- | --- | --- |
| `openai` | OpenAI Responses | Bearer; `store: false` |
| `vsegpt` | VseGPT Chat Completions | Bearer |
| `anthropic` | Claude Messages | `x-api-key` и версия API |
| `gigachat` | GigaChat Chat Completions | Ключ авторизации → OAuth → временный Bearer-токен |
| `openrouter` | OpenRouter Chat Completions | Bearer; fallback провайдеров отключён в запросе |

Это список реализованных адаптеров, **не результат живой проверки аккаунтов**. Модель должна поддерживать текстовые ответы и следовать JSON-инструкции. Доступность конкретного ID, контекст, лимиты и цена определяются аккаунтом провайдера. Модели с обязательным специальным reasoning-параметром или особым форматом ответа могут потребовать расширения адаптера. ID моделей вводятся при настройке подключения: автоматическая загрузка каталога пока не добавлена.

Произвольный URL из интерфейса или ответа модели не принимается. Для другого совместимого шлюза добавляется отдельный адаптер с проверенным адресом; одного рекламного обозначения «OpenAI-compatible» недостаточно для подтверждения совместимости.

## Куда вставить ключ

1. Запустить рабочий сервер по [инструкции](PROTOTYPE.md): Node.js 24, `npm ci`, `npm run prototype`. На Windows вместо двух команд можно открыть `start-assistant.cmd` в папке проекта. Дождаться запуска и оставить окно терминала открытым.
2. Открыть **http://127.0.0.1:8787/assistant/workspace** и войти с одноразовым кодом руководителя из терминала. Старое опубликованное Sites-демо не подключено к этому серверу и не содержит формы ключей.
3. Открыть **«Модели и роли» → «+ Добавить подключение»**. Указать название, выбрать провайдера, вставить уже имеющийся ключ в поле **«API-ключ»** и ввести ID доступных моделей — по одному на строке или через запятую. Для GigaChat выбрать scope. Нажать **«Сохранить подключение»**.
4. Включить аналитика, выбрать сохранённое подключение и модель, затем **«Сохранить назначения»**. Координатора и проверяющего можно подключить позже; у каждой роли свои провайдер и модель.
5. Открыть несекретную тестовую задачу и задать вопрос в консультации. Сохранение подключения не обращается к провайдеру. Отметка **«ключ сохранён»** подтверждает доступность секрета на сервере, а не правильность ключа, оплату или доступ к модели.

Для этого сценария `.env` и JSON-конфигурация не нужны. В новой базе все роли выключены. При отсутствии `ASSISTANT_AI_ENABLED` или пустом значении включением управляет руководитель через роли. Явное `ASSISTANT_AI_ENABLED=false` отключает вызовы на сервере, даже если роли включены; старую такую настройку нужно изменить перед запуском.

### Изменение подключения и хранение

Кнопка **«Изменить / заменить ключ»** открывает сохранённое подключение с пустым полем ключа. Пустое поле сохраняет прежний ключ; новый ключ заменяет его сразу, без перезапуска. Для другого провайдера создаётся отдельное подключение. Один и тот же провайдер может иметь несколько подключений с разными ключами.

Настройки и назначения хранятся в SQLite. Введённые через форму ключи сохраняются там зашифрованными AES-256-GCM. Ключ шифрования создаётся в `ASSISTANT_DATA_DIR/llm-master.key` (по умолчанию `.data/llm-master.key`); на POSIX — права `0600`. API не возвращает сохранённый секрет, приложение не записывает его в localStorage/sessionStorage. Форма доступна только руководителю; запись требует действующего сеанса, Origin, CSRF и актуальной версии настроек.

База и файл шифрования нужны вместе. `npm run memory:backup` создаёт рядом с копией базы файл `<имя-копии>.sqlite.llm-key`, если в базе есть подключения из интерфейса. При восстановлении в новый каталог данных положить базу как `assistant.sqlite`, а этот файл как `llm-master.key`, сохранив закрытые права доступа. Обе копии содержат данные для восстановления секретов; хранить их вне Git с ограниченным доступом. Шифрование базы не защищает от полного доступа к работающему серверу. Потеря файла шифрования не приводит к его молчаливой замене поверх существующих ключей.

### Дополнительный вариант: конфигурация администратора

Можно оставить ключи в окружении процесса. Скопировать `config/llm.example.json` в `config/llm.local.json`, удалить ненужные записи и заменить `REPLACE_WITH_MODEL_ID` реальными ID. В локальном `.env` указать `ASSISTANT_LLM_CONFIG=config/llm.local.json` и секреты с именами `ASSISTANT_LLM_KEY_*`. Значения ключей не помещаются в JSON. Затем запустить `node --env-file=.env scripts/prototype.mjs`.

Такие подключения доступны вместе с подключениями из формы. Они помечены **«Задано на сервере»** и редактируются в файле; для смены ключа в окружении процесс нужно перезапустить. Настройки ролей по-прежнему меняются в интерфейсе. ID подключений должны быть уникальны.

Минимальное подключение выглядит так (ID модели нужно заменить):

```json
{
  "connections": [{
    "id": "vsegpt-work",
    "label": "VseGPT · рабочий",
    "provider": "vsegpt",
    "credentialEnv": "ASSISTANT_LLM_KEY_VSEGPT",
    "models": ["REPLACE_WITH_MODEL_ID"],
    "maxOutputTokens": 2048
  }]
}
```

Файл ограничен 64 КБ и 20 записями; интерфейс позволяет добавлять подключения до общего количества 20. В каждом подключении — до 50 моделей. `maxOutputTokens` в файле допускает 256–8192 токена на вызов; для нового подключения из формы используется 2048.

### GigaChat

В поле API-ключа или переменную окружения передаётся **ключ авторизации**, а не краткоживущий access token. `scope` выбирается под договор: `GIGACHAT_API_PERS`, `GIGACHAT_API_B2B` или `GIGACHAT_API_CORP`. Адаптер использует OAuth `ngw.devices.sberbank.ru:9443/api/v2/oauth` и актуальный API `https://api.giga.chat/v1/chat/completions`. Токен обновляется при истечении срока; кеш разделён по подключению, ключу и scope. Секунды и миллисекунды в `expires_at` поддержаны.

Проверка TLS включена. Если окружению нужна дополнительная цепочка доверия, администратор устанавливает проверенные сертификаты и передаёт их через `NODE_EXTRA_CA_CERTS` при старте Node. Отключать проверку сертификата не требуется.

### Docker

Базовый `compose.prototype.yaml` запускается без ключей; затем их можно добавить в интерфейсе. База и `llm-master.key` сохраняются вместе в постоянном томе `/data`:

```sh
docker compose -f compose.prototype.yaml up --build
```

Для дополнительного варианта с `.env` и `config/llm.local.json`:

```sh
docker compose -f compose.prototype.yaml -f compose.ai.yaml up --build
```

Дополнение читает `.env` и монтирует `config/llm.local.json` только для чтения. Секреты не копируются в образ. Базовый Compose использует `ASSISTANT_SERVER_ORIGIN` из окружения/.env либо `http://localhost:8787` по умолчанию. Для размещения указать точный HTTPS-адрес и настроить обратный прокси с сохранением Host. Дополнение явно сохраняет контейнерные host/port и постоянный том `/data`, даже если в `.env` записаны настройки локального Node-запуска. Docker-образ в текущей среде не собирался.

## Как выполняется вопрос

| Роль | Задача | Обязательность |
| --- | --- | --- |
| Координатор | Разбить вопрос, перечислить неизвестное, предложить порядок разбора | Необязательна |
| Аналитик | Сводка, препятствия, варианты решения, текст письма при необходимости | Нужна для включения консультаций |
| Проверяющий | Независимо сверить результат аналитика с прочитанными источниками | Необязательна; отказ блокирует публикацию ответа |

Роли идут последовательно. Каждая получает актуальную память одной задачи; выводы предыдущих ролей помечены как недоверенные предложения. Координатор не создаёт новые роли и не выбирает другие модели. Проверяющий должен сам получить цитируемый фрагмент, чтение аналитика не считается его чтением. Проверка цитат подтверждает происхождение текста, но не гарантирует смысловую правильность вывода модели.

Исполнитель разрешает только строго проверенные действия `read_source`, `answer`, `review`. Адреса, команды, отправки и изменение фактов из вывода модели не выполняются. Отдельный текстовый JSON-протокол выбран для совместимости адаптеров; провайдерные инструменты, MCP и произвольное выполнение кода не подключены.

При создании вопроса фиксируются подключения и модели. Изменение назначений действует на **следующий вопрос**. Изменение самого подключения до старта останавливает старый запрос; подмены провайдера не происходит. Ключ из формы заменяется без перезапуска, ключ из окружения — после перезапуска с новым значением. В карточке ответа есть **«Кто подготовил ответ»**, выбранные модели, итог проверки и понятная категория ошибки. В журнале SQLite сохраняются номера вызовов и доступные счётчики токенов, без ключей и сырых ошибок провайдера. Стоимость автоматически не рассчитывается.

Ограничения исполнения: до четырёх модельных вызовов на роль (до трёх дополнительных страниц источников), до 12 вызовов на консультацию, до восьми минут на весь запрос, 45 секунд на один HTTP-вызов, два одновременных задания на процесс. Нет автоматических повторов платных вызовов и перехода на другой ключ, провайдер или модель. Переполненный процесс отклоняет дополнительную консультацию видимой ошибкой; это не очередь фоновых заданий.

После изменения задачи, источников или прав результат не публикуется. Повтор браузерного запроса с тем же ID не создаёт новую консультацию. При остановке процесса незавершённое задание не возобновляет платные вызовы автоматически; при следующем чтении истории и по достижении десятиминутного срока оно становится ошибкой. Для повторной попытки пользователь задаёт новый вопрос. Это первая реализация для одного постоянного процесса; распределённый worker и устойчивое возобновление — отдельный этап.

## Границы этой поставки

- Роли подключены к **веб-консультациям по задаче**. Обычный разбор входящих статусов и краткая общая сводка пока используют правила. Текст ответа можно использовать как предложение или письмо; самостоятельной внешней отправки нет.
- Telegram-обвязка eve сохранена как прежний, ещё не проверенный вживую модуль. Её перенос на общий независимый маршрутизатор — следующий этап. MAX пока не реализован. Новые назначения не следует считать настройкой всех старых Telegram-инструментов.
- Проверены HTTP/SQLite/DOM и запросы адаптеров с подставленными ответами. Живые ключи, качество моделей, TLS конкретного сервера, Docker и полноценная браузерная отрисовка ещё требуют приёмки на выбранном окружении.
