# Закрытый размещённый пилот и перенос на другой сервер

Один руководитель, одна команда, только вымышленные данные. Это не production
для нескольких подразделений. GitHub хранит код; Node.js 24 обслуживает браузеры,
SQLite хранится на постоянном диске. Отдельная управляемая БД не требуется.

## Раздельные bootstrap и постоянный запуск

Локальные `npm run prototype` и `compose.prototype.yaml` остаются прежним демо.
Для размещения используется дополнительный `compose.hosted.yaml`: он запускает
`pilot-server.mjs`, **не создаёт примеры и не печатает приглашения при рестарте**.
Пустая база требует явного bootstrap до открытия доступа.

1. Подготовить Linux-сервер, Docker Compose, диск, закрытый административный доступ
   и HTTPS reverse proxy. Опубликовать только HTTPS (и HTTP для перенаправления/
   выдачи сертификата при необходимости); Node-порт 8787 оставить на loopback.
2. Взять `hosted.env.example` как образец. Задать реальный
   `ASSISTANT_SERVER_ORIGIN=https://ваш-домен` без пути. Proxy должен передавать
   исходный публичный `Host`: сервер проверяет его и Origin строго. HTTPS публичный;
   внутренний HTTP между proxy и loopback допустим. На proxy ограничить частоту
   запросов входа и размер тела; проверить права и сессии через публичный адрес.
3. Ниже `$ENV_FILE` означает абсолютный путь к подготовленному env-файлу, не ключ.
   Постоянное имя проекта `pulse-pilot` сохраняет привязку к тому же named volume:

```sh
# Выполняет оператор только после согласования конкретного сервера.
docker compose --env-file "$ENV_FILE" -p pulse-pilot -f compose.prototype.yaml -f compose.hosted.yaml build
# Один раз. Без --examples создаётся только руководитель; с флагом — вымышленные примеры.
docker compose --env-file "$ENV_FILE" -p pulse-pilot -f compose.prototype.yaml -f compose.hosted.yaml run --rm --no-deps assistant node scripts/bootstrap-hosted.mjs --examples
# Код одноразовый, 30 минут. Получать только в закрытом терминале, не в CI/public logs.
docker compose --env-file "$ENV_FILE" -p pulse-pilot -f compose.prototype.yaml -f compose.hosted.yaml run --rm --no-deps assistant node scripts/pilot-invite.mjs manager
docker compose --env-file "$ENV_FILE" -p pulse-pilot -f compose.prototype.yaml -f compose.hosted.yaml up -d
```

Bootstrap повторно не меняет существующую команду/задачи и не выпускает приглашений.
Обычный runtime не должен использовать `prototype.mjs`. Не публиковать его журналы,
старые коды, резервные копии или каталог данных. Не выполнять `down -v`.
Hosted overlay явно выключает AI и внешнюю доставку; не сочетать его с `compose.ai.yaml`.
Включение живых моделей — отдельное решение и проверка бюджета/качества.

## Переносимость: что переносим

На новом сервере нужны тот же проверенный коммит, Node.js 24 (или образ), настройки
окружения и **согласованная копия SQLite**. Если сохранены подключения моделей,
нужен также парный файл ключа восстановления. Облачная привязка приложению не нужна.
Не переносить только `dist/`: это не база и не серверные сессии.

1. Подготовить новый сервер и HTTPS, не переключая пользователей. Для переноса
   использовать тот же коммит; обновление схемы/версии приложения — отдельный шаг.
2. Назначить короткое окно остановки записи. Закрыть входящий доступ и остановить
   старый процесс/контейнер, чтобы очереди и автоопрос тоже не меняли БД. При живых
   провайдерах сначала отдельно разобраться с running/unknown вызовами — не replay.
3. Выполнить существующий `scripts/backup-state.mjs` с **тем же** `ASSISTANT_DATA_DIR`
   и новым путём копии. Команда работает и на остановленной БД, делает `VACUUM INTO`
   и проверку целостности. В Docker запустить её отдельным `compose run --rm --no-deps`
   с теми же файлами/именем проекта; копия в `/data` сама по себе ещё не off-server backup.
4. Защищённо перенести `.sqlite` и, если создан, `.sqlite.llm-key` вне исходного
   сервера. Не Git, не публичная ссылка. Передачу и хранение отдельно защитить.
5. В новом **пустом**, закрытом каталоге данных установить копию как `assistant.sqlite`,
   парный ключ как `llm-master.key` (0600, владелец — пользователь приложения).
   Не добавлять старые `-wal`/`-shm`. Для Docker заполнить новый постоянный том;
   не оставлять данные только в файловой системе контейнера. Старый том сохранить.
6. Запустить только новый сервер с AI/delivery выключенными. Проверить вход новым
   приглашением, задачи, источники, отчёты, роли и перезапуск. При смене домена браузер
   не передаст старую cookie — вход заново ожидаем. Старые записи сессий в копии БД
   существуют до expiry/logout; не считать перенос автоматическим отзывом сессий.
7. Переключить DNS/proxy после проверки и открыть доступ. Старый сервер оставить
   остановленным: одновременно писать в две независимые копии нельзя. Откат после
   появления новых записей требует отдельного переноса новых данных, не простого
   возврата DNS. Нулевой простой не обещается; DNS-кэши могут продлить переключение.

Внешние credentials, DNS, TLS, firewall, расписание off-server backup и доступ к
провайдерам на новом хосте проверяются отдельно. Копия ключа восстанавливает только
сохранённые в приложении зашифрованные подключения, а не все внешние настройки.

## Доказательства и границы проверки

### Имя cookie HTTPS и обновление существующего пилота

При HTTPS сервер использует `__Secure-lazy_work_session` с `Secure`, `HttpOnly`,
`SameSite=Strict` и прежним `Path=/assistant`. Имя выбирается по проверенному
`ASSISTANT_SERVER_ORIGIN`, а не по заголовкам запроса или proxy. Для разрешённого
локального HTTP остаётся `lazy_work_session` без `Secure`; публичный HTTP origin
по-прежнему отклоняется. HTTPS не принимает прежнее непрефиксное имя: после
обновления участникам понадобятся новые одноразовые приглашения и повторный вход.
Записи старых сессий остаются в БД до истечения срока; смена имени не является
их отзывом. Откат на старую версию снова сделает неистёкшие старые cookie пригодными.

Это адресует требование [ASVS v5.0.0-3.3.1](https://github.com/OWASP/ASVS/blob/v5.0.0/5.0/en/0x12-V3-Web-Frontend-Security.md)
для HTTPS, но не означает полного соответствия ASVS. Более строгое требование
3.3.3 уровня L2 о `__Host-` этим изменением не закрывается. Локальный HTTP —
исключение для разработки, не соответствующее защищённому production transport.
Тест `Cookie namespace` в `tests/pilot-api.test.mjs` проверяет выдачу, чтение и
удаление cookie обоих режимов, неверное/дублированное имя, сохранение атрибутов,
игнорирование `X-Forwarded-Proto` при выборе имени и отказ небезопасного origin.

`node --test tests/hosted-portability.test.mjs` использует только синтетические
записи и фиктивный ключ в отдельных временных каталогах. Проверяет однократную
инициализацию, неизменность повторного запуска, согласованный backup, точное
восстановление таблиц с задачами/источниками/отчётами/auth, расшифрование фиктивного
ключа новым процессом и настоящий HTTP-вход после переноса. Два запуска реального
`pilot-server.mjs` подтверждают сохранность сессии/данных и отсутствие новых кодов
в startup output. Исходная БД не меняется при работе с восстановленной копией.

Это проверка локального Node runtime, не сборка Docker, не тест публичного TLS,
не нагрузочная проверка, не живой провайдер и не проверка облачного восстановления.
Перед показом нужны две браузерные роли, телефон, проверка backup на целевом хосте
и сохранности после его перезапуска. Само наличие этих файлов ничего не размещает.
