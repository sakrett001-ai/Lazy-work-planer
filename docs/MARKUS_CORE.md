# Markus consultation policy and broker

This source candidate keeps AI, delivery and broker use disabled by default. Publication is not deployment or permission to enable paid calls.

## Runtime boundaries

The persistent Node consultation runner applies host-owned instructions and strict role-specific JSON. The analyst and reviewer cannot change task facts, deadlines or acceptance. Reviewer rejection withholds the draft and exposes only a deterministic safe notice. Disabled review is not labelled independently checked. Model self-review is not proof of correctness.

Task context is actor-scoped. Registered requester identity, task/context versions, exact source citations and structured acceptance evidence are checked before publication. Source arrival time is not automatically event time or truth. Prior assistant answers are not supplied as free-chat history. Existing stored answers remain readable; new ambiguous protocol output fails closed.

## Optional isolated broker

`broker-allocation.ts` reserves an explicit operator-approved allocation before exclusive ledger initialization. Restart opens an existing ledger; it does not reset budget. `broker-core.ts` authenticates bounded requests and reserves money and call capacity before dispatch. Unknown outcomes retain reservations and halt admission; there is no automatic retry or refund.

`broker-worker.ts`, the Python peer gate and fixed launcher compose the existing ledger with a server-owned provider transport. The application route is keyless and has no direct-provider fallback. Unix peer credentials and HMAC authenticate the application process, not the human user; task authorization remains the application's responsibility. A compromised authorized application can submit requests within broker caps.

Provider credentials belong only to the worker. Model IDs, policy hashes, tariffs, token bounds and paths require explicit trusted configuration. Example configuration is not authorization to spend or deploy. No live credentials or account identifiers are distributed here.

## Activation requirements

A separately reviewed deployment must establish dedicated service identity, restricted credential/ledger/socket ownership, approved fixed models and current pricing, bounded data scope and allocation, network restrictions, disable/rollback behavior and end-to-end validation. Preserve ledgers and unknown reservations on code rollback. These checks do not authorize installing services or changing firewall rules.

See [public verification scope](MARKUS_PUBLIC_VERIFICATION.md). Public synthetic regression tests exercise host enforcement, not general model quality or production isolation.
